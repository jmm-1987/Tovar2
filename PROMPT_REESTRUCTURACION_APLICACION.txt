PROMPT PARA REESTRUCTURAR Y REGENERAR LA APLICACIÓN TOVAR2
================================================================================

CONTEXTO Y OBJETIVO
================================================================================
Necesito regenerar desde cero una aplicación web Flask para la gestión integral 
de una empresa de textil personalizado (confección, bordado, serigrafía, sublimación).

La aplicación actual funciona correctamente pero necesita una mejor arquitectura:
- Mejor organización de clases y separación de responsabilidades
- Facturación más aislada y modular
- Código más mantenible y escalable
- Mismas funcionalidades pero con mejor estructura

TECNOLOGÍAS Y STACK TECNOLÓGICO
================================================================================
- Backend: Flask 3.0+ (Python)
- Base de datos: SQLite (compatible con PostgreSQL para producción)
- ORM: SQLAlchemy (Flask-SQLAlchemy 3.1+)
- Autenticación: Flask-Login
- Email: Flask-Mail
- PDF: Playwright (generación de PDFs desde HTML)
- Frontend: HTML, CSS, JavaScript (vanilla, sin frameworks)
- Templates: Jinja2
- Servidor: Gunicorn (producción)
- Variables de entorno: python-dotenv
- Otros: openpyxl (Excel), requests, paramiko (SFTP)

MODELOS Y ENTIDADES PRINCIPALES
================================================================================

1. USUARIOS Y AUTENTICACIÓN
   - Usuario: usuarios del sistema (roles: comercial, administracion, supervisor, usuario)
   - Comercial: vinculado a Usuario, puede crear pedidos

2. CLIENTES
   - Cliente: información completa del cliente, puede tener acceso web
   - CategoriaCliente: categorías configurables
   - DireccionEnvio: direcciones de envío del cliente
   - PersonasContacto: personas de contacto (puede ser tabla o JSON)

3. PRODUCTOS
   - Prenda: maestros de prendas (nombre, tipo, descripción)

4. SOLICITUDES/PRESUPUESTOS (PRESUPUESTOS = solicitudes en estado inicial)
   - Presupuesto: solicitud inicial (número formato aamm_contador, ej: 2601_01)
     - Estados: presupuesto, rechazado, aceptado, mockup, en preparacion, 
       revision y empaquetado, entregado al cliente
     - Subestados: para mockup (encargado a, REVISIÓN CLIENTE, CAMBIOS 1/2, 
       RECHAZADO, aceptado) y en preparacion (hacer marcada, imprimir, 
       calandra, corte, confeccion, sublimacion, bordado)
   - LineaPresupuesto: líneas del presupuesto (prenda, cantidad, talla, 
     precio_unitario, descuento, precio_final, importe)
   - RegistroEstadoSolicitud: historial de cambios de estado

5. PEDIDOS (opcional, puede fusionarse con Presupuesto cuando estado = "aceptado")
   - Pedido: puede venir de Presupuesto o ser independiente
   - LineaPedido: líneas del pedido

6. FACTURACIÓN (MÓDULO AISLADO - CRÍTICO)
   - Factura: facturas directas (NO vinculadas a presupuestos)
     - serie, numero, fecha_expedicion, tipo_factura
     - cliente_id, datos_cliente (snapshot)
     - base_imponible, tipo_iva, iva, total
     - estado, huella_verifactu (integración Verifactu)
   - LineaFactura: líneas de la factura
     - descripcion, cantidad, talla, precio_unitario, descuento, 
       precio_final, importe
     - es_linea_texto (para líneas informativas sin precio)
   
   - Albarán/Delivery Note: puede ser tipo especial de Factura (tipo='albaran') 
     O entidad separada
     - Mismo formato que Factura pero SIN precios visibles en PDF
     - Puede tener presupuesto_id vinculado
     - Líneas pueden ir sin precios
     - Líneas de texto permitidas

7. TICKETS (Facturas Simplificadas)
   - Ticket: facturas simplificadas (tipo F2)
   - LineaTicket: líneas del ticket

8. GASTOS
   - Proveedor: proveedores
   - FacturaProveedor: facturas de proveedores
   - Empleado: empleados
   - Nomina: nóminas de empleados

9. CONFIGURACIÓN
   - PlantillaEmail: plantillas de email configurables
   - Configuracion: configuración general
   - DiaFestivo: días festivos configurables

5. TICKETS (Facturas Simplificadas)
   - Crear ticket tipo F2
   - Cálculo IVA: incrementar o desglosar
   - Generación PDF

6. PEDIDOS (si se mantiene separado de Presupuesto)
   - Gestión de pedidos en fabricación

   - Gestión de proveedores

    - Gestión de usuarios

    - Configuración general

REQUISITOS ESPECÍFICOS DE ARQUITECTURA
================================================================================

1. FACTURACIÓN DEBE ESTAR COMPLETAMENTE AISLADA
   - Módulo separado en services/invoice_service.py
   - Rutas en api/invoices/ y api/delivery_notes/
   - Validadores específicos
   - Repositorio independiente (opcional pero recomendado)
   - NO mezclar lógica de facturas con presupuestos/pedidos

2. SEPARACIÓN DE RESPONSABILIDADES
   - Routes: Solo manejo de requests/responses, validación básica
   - Services: Toda la lógica de negocio
   - Repositories: Acceso a datos (opcional, puede usar modelos directamente)
   - Models: Solo definición de entidades y relaciones

3. USAR PATRÓN FACTORY PARA FLASK APP
   - app/__init__.py con create_app() function
   - Configuración por entorno (development, production)
   - app.py simple que llama a create_app()

4. SERVICIOS COMO CLASES O FUNCIONES
   - InvoiceService: clase con métodos para operaciones de facturación
   - DeliveryNoteService: clase con métodos para albaranes
   - PDFService: clase para generación de PDFs (común)
   - Etc.

5. VALIDACIÓN
   - Validadores en utils/validators.py (genéricos)
   - Validadores específicos en módulos (ej: invoices/validators.py)
   - Usar marshmallow o pydantic (opcional pero recomendado)

6. MANEJO DE ERRORES
   - Excepciones personalizadas por dominio
   - Manejo centralizado de errores
   - Logging apropiado

7. CÁLCULOS FINANCIEROS
   - Usar Decimal para todos los cálculos monetarios
   - Servicio de cálculo separado (ej: InvoiceCalculator)
   - Validar cálculos en tests

EJEMPLO 4: Factory Pattern
--------------------------
# app/__init__.py

from flask import Flask
from app.config import Config
from app.extensions import db, login_manager, mail

def create_app(config_class=Config):
    app = Flask(__name__)
    app.config.from_object(config_class)
    
    # Inicializar extensiones
    db.init_app(app)
    login_manager.init_app(app)
    mail.init_app(app)
    
    # Registrar blueprints
    from app.api.auth.routes import auth_bp
    from app.api.invoices.routes import invoices_bp
    from app.api.delivery_notes.routes import delivery_notes_bp
    # ... otros blueprints
    
    app.register_blueprint(auth_bp)
    app.register_blueprint(invoices_bp, url_prefix='/api')
    app.register_blueprint(delivery_notes_bp, url_prefix='/api')
    
    return app


# app.py (punto de entrada)

from app import create_app
from app.config import DevelopmentConfig

app = create_app(DevelopmentConfig)

if __name__ == '__main__':
    app.run(debug=True)
